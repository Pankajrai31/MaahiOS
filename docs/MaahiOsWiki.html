1. Drivers

Hardware abstraction layer for MaahiOS

MaahiOS drivers provide a unified interface between hardware devices and the kernel. All drivers follow a consistent architecture pattern that enables the Device Manager to manage them uniformly through a standard set of operations.

Drivers run in Ring 0 (kernel space) and are accessed by user applications through syscalls via the Device Manager.

§ 1.1 Driver Architecture

Every MaahiOS driver follows a 3-part pattern:

1️⃣

Registration

Call register_device() to add driver to Device Manager's array

2️⃣

Handler Functions

Implement device_ops_t interface (open, close, read, write, ioctl, poll)

3️⃣

Device-Specific

Hardware-specific functions (IRQ handlers, port I/O, etc.)

Data Flow
User App → Syscall (INT 0x80) → Device Manager → Driver → Hardware

§ 1.2 Device Operations Structure

All drivers must implement the device_ops_t structure, which provides a uniform interface: 

typedef struct device_ops {
    int  (*open)(int flags);
    int  (*close)(int handle);
    int  (*read)(int handle, void* buffer, size_t size);
    int  (*write)(int handle, const void* buffer, size_t size);
    int  (*ioctl)(int handle, int cmd, void* arg);
    int  (*poll)(int handle);
} device_ops_t;
Function Purpose Returns
open() Initialize device access Handle (≥0) or error (<0)
close() Release device 0 on success
read() Read data from device Bytes read or error
write() Write data to device Bytes written or error
ioctl() Device-specific commands Command-dependent
poll() Check if data available 1 = ready, 0 = not ready

§ 1.3 Driver Registration

Drivers register with the Device Manager using register_device(). This adds the driver to a static array in kernel memory: 

// In driver's init function:
static device_ops_t my_driver_ops = {
    .open  = my_dev_open,
    .close = my_dev_close,
    .read  = my_dev_read,
    .write = my_dev_write,
    .ioctl = my_dev_ioctl,
    .poll  = my_dev_poll
};

int my_driver_init(void) {
    // ... hardware initialization ...
    
    register_device(DEV_MY_DEVICE, "mydevice", &my_driver_ops);
    return 0;
}
Device IDs (from device_manager.h)
DEV_MOUSE = 1
DEV_KEYBOARD = 2
DEV_DISPLAY = 3
DEV_DISK = 4
DEV_TIMER = 6
DEV_RTC = 7

§ 5.3 Shared I/O (io.h)

UTILITY

Centralized port I/O functions used by all drivers and kernel managers. Single source of truth for inb/outb and related functions. Prevents duplicate inline assembly definitions across files.

📍 Location
system/libraries/shared/io.h
📊 Users
10 files (all drivers + irq_manager + pit)
Functions
inb(port) / outb(port, val) 8-bit port I/O
inw(port) / outw(port, val) 16-bit port I/O
inl(port) / outl(port, val) 32-bit port I/O
io_wait() Wait ~1μs via port 0x80
⚠️ Rules
• NEVER define your own inline inb/outb — always include this header
• NEVER expose port I/O to Ring 3 via syscalls — security violation
• All functions are static inline — zero overhead, no linker symbols

6. Kernel Managers

Ring 0 kernel subsystems — all verified ✅

✅ VERIFIED

§ 6.1 Overview

Managers are kernel-space services that run in Ring 0. They own all kernel state and are accessed from user-space exclusively through syscalls (INT 0x80). Each manager follows a consistent pattern: *_init() → returns int (0 = success).

managers/
├── cell/ Key-value store
├── device/ Device registration + dispatch
├── gdt/ Global Descriptor Table
├── grub_module/ GRUB module loading
├── interrupt/ IDT, exceptions, stubs
├── irq/ IRQ routing, PIC
├── klog/ Kernel logging (serial COM1)
├── memory/ PMM, paging, kheap
├── process/ Process lifecycle
├── ring3/ Ring 0→3 switching
├── scheduler/ Round-robin scheduling
├── shm/ Shared memory regions
├── syscall/ Dispatcher + 9 handler files
├── time/ Time computation from RTC+ticks
└── timer/ PIT (Programmable Interval Timer)

🚀 Kernel Boot Initialization Order

1 klog_manager_init() → Serial output ready
2 gdt_init() → Segment descriptors + TSS
3 idt_init() → Interrupt Descriptor Table
4 irq_manager_init() → PIC remapping (IRQ0→0x20)
5 pmm_init(mbi) → Physical memory bitmap
6 paging_init(mbi) → Page tables + identity map
7 kheap_init() → Kernel heap allocator
8 pit_init(50) → Timer at 50 Hz
9 device_manager_init() → Device array + driver init
10 time_manager_init() → Boot time snapshot
11 shm_manager_init() → SHM region tracking
12 cell_manager_init() → Key-value store
13 process_manager_init() → Process table
14 scheduler_init() → Scheduling queues
15 grub_module_manager_init(mbi) → Parse GRUB modules
16 syscall_manager_init() → Register 47 handlers

§ 6.2 Core Managers

Low-level infrastructure managers initialized during early boot.

📋

GDT Manager

managers/gdt/

Sets up segment descriptors for Ring 0/3 code+data and the TSS (Task State Segment) for privilege switching.

gdt_init()→ int
0x08 Kernel Code
0x18 User Code
0x28 TSS
⚡

Interrupt + IRQ Manager

managers/interrupt/ + managers/irq/

IDT setup for 256 interrupt gates. IRQ manager remaps PIC (IRQ0→0x20, IRQ8→0x28) and provides EOI handling.

idt_init()→ int (256 gates)
irq_manager_init()→ int (PIC remap)
irq_register_handler(irq, fn)→ void
INT 0x80 gate has DPL=3 (user-accessible for syscalls)
🧠

Memory Manager (PMM + Paging + kheap)

managers/memory/

Physical page allocator (bitmap), virtual memory with page tables, and kernel heap for dynamic allocation.

pmm_init(mbi)→ int (page bitmap)
paging_init(mbi)→ int (page tables)
kheap_init()→ int (heap at 0x400000+)
pmm_alloc_page()→ void* (4KB page)
pmm_free_page(addr)→ void
⏱️

Timer (PIT)

managers/timer/

Programmable Interval Timer — generates IRQ0 at configured frequency (50 Hz). Drives the scheduler tick and time tracking.

pit_init(frequency)→ int (sets channel 0)
pit_get_ticks()→ uint64_t
Port 0x40 (Channel 0) | Port 0x43 (Command) | Uses shared io.h
🔄

Scheduler

managers/scheduler/

Round-robin preemptive scheduler triggered by PIT timer interrupt. Manages process time slices and context switching.

scheduler_init()→ int
scheduler_enable() / disable()→ void
scheduler_add_process(...)→ void
scheduler_get_current_pid()→ int

In-kernel key-value store. Executives register their SHM IDs here so other processes can discover them.

🕐

Time Manager

managers/time/

Computes current datetime from RTC boot snapshot + PIT tick count. Provides uptime, unix time, and tick queries.

time_manager_init()→ int

Klog Manager

managers/klog/

Kernel logging via serial COM1 (0x3F8). Supports kernel [K] and user [U] log origins with timestamps.

📦

GRUB Module Manager

managers/grub_module/

Parses GRUB multiboot module list. Provides access to loaded binaries (executives, apps) by index or name.

grub_module_manager_init(mbi)→ int

🚪

Ring3 Switch

managers/ring3/

One-way transition from Ring 0 to Ring 3. Sets up user-mode segments and jumps via IRET.

ring3_switch(entry)→ noreturn
manual_first_switch()→ noreturn

7. Syscall Layer

INT 0x80 dispatch — 64 syscalls across 10 domains ✅

✅ 64 VERIFIED

§ 7.1 Overview

The syscall layer is the only way Ring 3 code can access kernel services. User code triggers INT 0x80 with EAX = syscall number and arguments in EBX, ECX, EDX, ESI, EDI.

Syscall Flow

8. Executives

Ring 3 service processes that mediate between user processes and kernel syscalls

8.1 Overview

Executives are Ring 3 (user-space) service processes that run alongside application processes. Each executive owns a specific domain of functionality and provides services to other processes via shared memory (SHM) request/response queues. Executives are started by sysman (PID 1) during boot.

Communication Pattern

Client Process                     Executive Process
──────────────                     ─────────────────
libXXX_write(key, val)
  → _try_init()                    _start() → main()
    → cell_read("system.exec.XXX.req_shm")    → SHM_CREATE → CELL_WRITE(shm_id)
    → SHM_ATTACH(shm_id)                      → loop:
  → exe_request_queue_push(req)    →   exe_request_queue_pop(req)
  → SYS_SLEEP poll for response    →   handle_request(req)
  ← exe_response_queue_pop_by_id() ←   exe_response_queue_push(resp)

Boot Order

1. sysman (PID 1) starts

2. Log Executive (PID 2) — loaded 1st

3. Cell Executive (PID 3) — loaded 2nd

4. Process Executive (PID 4) — loaded 3rd

5. Memory Executive (PID 5) — loaded 4th

6. Disk Executive — loaded 5th

7. FS Executive — loaded 6th

8. GUI Executive — loaded 7th

9. I/O Executive — loaded 8th

10. WM Executive — loaded 9th

11. Orbit + Terminal — loaded last

SHM Queues

Request queue: client → executive

Response queue: executive → client

Discovered via cell registry

Common Framework

executive_queue.h/c

exec_request_queue_t, exec_response_queue_t

push/pop with spinlock protection

8.4 Process Executive

🔄

Process Executive — PID 4

system/executives/processexecutive/process_executive.c • Load addr: 0xA00000

The Process Executive manages user-space process lifecycle — creating, terminating, and querying processes. It acts as a smart, memory-aware policy gatekeeper between user apps and the kernel process_manager. Uses dual SHM queues (request + response) and relies on liblog (auto-init) for logging and libcell (auto-init) for cell publishing. Loaded third by sysman (after Log and Cell Executives). Periodically monitors system memory via SYS_GET_MEM_INFO and publishes metrics to the cell registry. Refuses process creation when memory pressure is critical (<5% free).

Startup Sequence

1. _start → exe_process_main()

2. Create request SHM + response SHM

3. Attach both into own address space

4. Initialize both queues (req + resp)

5. Register via libcell_write():

• system.exec.process.req_shm

• system.exec.process.resp_shm

Request Handlers (5)

PROC_OP_CREATE → memory guard + module_copy + process_create
PROC_OP_KILL → SYS_PROCESS_KILL
PROC_OP_GET_INFO → SYS_PROCESS_INFO
PROC_OP_GET_COUNT → SYS_PROCESS_GET_COUNT
EXEC_OP_PING → returns 0 (alive check)

Create Pipeline

1. Client sends PROC_OP_CREATE with module_index + load_address

2. Executive checks memory pressure — refuses with EXEC_ERR_NO_MEMORY if critical

3. Executive calls SYS_MODULE_COPY to copy GRUB module to load_address

4. Executive calls SYS_PROCESS_CREATE with entry point = load_address

5. Updates system.process.active_count cell

6. Returns new PID in response

SYS_GET_MEM_INFO244
SYS_YIELD1

Logging via liblog (auto-init) · Cell publishing via libcell (auto-init)

Smart Memory Monitoring

Periodic Monitoring

Every 200 idle cycles (~4 seconds at 50Hz), calls SYS_GET_MEM_INFO to query PMM total/free/used bytes. Publishes to cell registry: system.memory.total, system.memory.free, system.memory.used.

Memory Pressure Levels

0 = Normal — free > 10% of total.
1 = Warning — free < 10% of total (logged).
2 = Critical — free < 5% of total (process creation refused).

Active Process Count

After every successful create or kill, calls SYS_PROCESS_GET_COUNT and writes result to system.process.active_count cell.

Create Guard

If g_memory_pressure >= 2 (critical), PROC_OP_CREATE returns EXEC_ERR_NO_MEMORY (-5) without attempting the syscall.

9. Libraries

User-space client libraries that abstract executive communication

9.1 Overview

Libraries are client-side code that run inside the calling process's address space. They provide a simple API that hides the complexity of SHM queue discovery, attachment, and request/response marshalling. All libraries follow the lazy auto-init pattern.

Lazy Auto-Init Pattern

Every API call:
  1. if (!g_initialized) → _try_init()
     a. Read executive's SHM ID from cell registry
     b. Attach SHM into THIS process's address space
     c. Set g_initialized = 1
  2. if (g_queue) → push request to SHM queue
  3. else → fallback to direct kernel syscall

Key Design Decisions

• No explicit init() needed — auto-called on first use

• Graceful fallback — works even if executive not running

• Per-process state — each process attaches SHM independently

• init() still available — can be called explicitly if needed

Location

🗄️

libcell — Cell Registry Library

system/libraries/libcell/libcell.c • Client for Cell Executive

Provides the cell key-value store API for user processes. Auto-initializes on first call by discovering two SHM queues from the cell registry: system.exec.cell.req_shm and system.exec.cell.resp_shm. Falls back to direct SYS_CELL_* kernel syscalls if the Cell Executive is not running.

1. libcell_write() called

2. _libcell_try_init() if !g_initialized

→ push request to SHM

10. Applications & System Programs

User-space programs — 3 system programs + 12 GUI/console apps

10.1 System Programs

System programs are essential processes loaded by sysman during boot. They run continuously and provide core infrastructure services.

⚙️ sysman (PID 1)

system/systemprograms/sysman/sysman.c

First user process. Loads all 9 executives, then Orbit and Terminal via GRUB modules. Monitors executive health and uses raw syscalls (no executive path available yet).

🖥️ orbit (Desktop Shell)

system/systemprograms/orbit/orbit.c

Desktop shell — renders wallpaper, taskbar with clock, desktop icons, Start Menu. Launches apps via libprocess. Reads icons via libfs + libbmp. Draws directly to framebuffer via libgui.

💻 terminal

system/systemprograms/terminal/terminal.c

Console host — renders text output from console .mex apps using font8x16 VGA bitmap font. Reads from app's SHM console buffer, provides scrollback, keyboard input forwarding.

10.2 User Applications (12)

All apps are compiled as .mex (MaahiOS Executable) binaries, loaded from the ISO filesystem at runtime. Console apps use libconsole for output; GUI apps use libwindow for windowed rendering via the WM Executive.

👋 hello

apps/hello/ • console

Hello World — minimal console app that prints a greeting. Template for new console apps.

🎨 hellogui

apps/hellogui/ • gui (windowed)

Hello GUI — minimal windowed app. Template for new GUI apps using libwindow.

🎮 boxdrop

apps/boxdrop/ • gui (windowed)

BoxDrop — falling-block puzzle game. Demonstrates keyboard input, tick-based animation, and custom rendering in a window.

📊 procman

apps/procman/ • console

Process Manager — lists all running processes with PID, name, and state. Uses libprocess.

💾 diskman

apps/diskman/ • console

Disk Manager — lists all disk devices with size, type, and partition info. Uses libdisk.

📁 fileman

apps/fileman/ • console

File Manager — browses ISO9660 filesystem, lists directories and files. Uses libfs.

ℹ️ sysinfo

⏻ shutdown

📋 procexp

💿 diskexp
