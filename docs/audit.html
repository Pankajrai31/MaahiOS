1d. Window Management Flow

Complete trace of window lifecycle: creation, rendering, input routing, taskbar integration, and destruction.

Window Creation

Zero-copy SHM surface model
App calls window_create() → libwm_create() → WM Executive creates SHM surface → both app and WM attach same SHM. App writes pixels directly; WM reads during compositing. No copy.

Compositing

Damage-rect compositor with partial flip
Apps signal WM_CMD_DAMAGE (async, fire-and-forget). WM accumulates dirty rect, composites via painter's algorithm (desktop → windows bottom-to-top → NR dialog), flips only the dirty rect via DISPLAY_IOCTL_FLIP_RECT.

Input Routing

DeviceMechanismFocus Model
KeyboardIO Exec → SHM ring buffer → apps readFocus-gated via focused_pid
MouseIO Exec → SHM state slot → all apps readNo gating — apps self-filter by window bounds

Taskbar / Orbit

Cell-based publish/subscribe
WM publishes system.taskbar.windows on every state change. Orbit polls and does change detection. Minimize/restore use per-PID signal cells.

Issues Found

Minimize/Restore cell signaling is race-prone
Single-value cells (CELL_TASKBAR_RESTORE, CELL_TASKBAR_MINIMIZE) store one PID at a time. If two windows minimize simultaneously, one signal is lost. Low severity with max 6 windows.
Drag outline bypasses WM compositor
xor_drag_outline() writes directly to backbuffer via gui_get_framebuffer(), bypassing the compositor. Potential visual glitch if WM composites the same region mid-drag. Cleaned up by recomposite after drag ends.
WM Executive reads display cells with raw SYS_CELL_READ
In init_display(), WM uses raw syscalls instead of libcell_read(). Likely a bootstrap-timing workaround. Minor layering inconsistency.
Heartbeat has redundant SHM table path
Heartbeat uses both a SHM table and queue-based commands, but clients only send queue heartbeats. The SHM table is effectively a mirror — could be simplified.
Single global damage rect can over-composite
All damage is unioned into one rect. Distant windows cause full-screen recomposite. A damage-list approach would reduce overdraw at higher resolutions.

2.1 Virtual Memory & Paging

Current State: Partial — Identity-Mapped with Per-Process Directories Needs Work

What exists: Two-level x86 page tables, 128 MB kernel identity map (virt == phys 0x00–0x08000000), per-process page directories via paging_clone_kernel_directory(), CR3 switched on context switch, WP bit enabled in CR0, bitmap-based PMM with contiguous multi-page alloc.

GapPriorityEffort

No swap / page-out — all pages resident; no disk-backed virtual memoryHighLarge

2.2 Threading

Current State: Not Supported — Processes Only Missing

What exists: Round-robin scheduler across processes. PCB has no thread list, no thread ID, no TLS pointer. One execution context per process. Spinlocks exist in user-space executive queues for SHM synchronization only.

2.11 Priority Roadmap — Road to Commercial Viability

Tier 1: Blockers — System is unsafe/broken without these Do First
  1. FPU init + save/restore on context switch — floating-point is silently corrupt today
  2. Fix IOPL=3 — set IOPL=0 for user processes, block direct port I/O
  3. Kernel memory protection — remove PAGE_USER from kernel identity map
  4. Syscall pointer validation — verify user pointers don't reference kernel memory
  5. Page fault handler — at minimum, clean termination with diagnostics
Tier 2: Core OS Competitiveness Build Next
  1. Threads (pthreads-like API) + synchronization primitives
  2. libc port (Newlib or musl) — unlocks porting of existing software
  3. ELF loader — replaces .mex, standard toolchain compatibility
  4. DHCP client — network auto-configuration
  5. USB stack (at least UHCI/EHCI for keyboard, mouse, mass storage)
  6. Journaling filesystem or adopt ext2 driver
Tier 3: Developer Platform Long-Term
  1. POSIX pipes + signals — standard IPC
  2. DMA for disk and network — performance
  3. ACPI — proper shutdown, sleep, power management
  4. select/poll or event-based I/O
  5. GDB remote stub for debugging
  6. Dynamic linker — shared libraries

5.5 What's Working Well

Strengths to build on Solid
  • Executive architecture — All 10 executives are fully compliant with the layering model. The SHM queue IPC pattern is clean and consistent.
  • Device manager HAL — Function-pointer dispatch creates genuine hardware abstraction. Adding new drivers requires only registering ops.
  • Networking stack — From NIC driver to TLS 1.2 to a working browser is a remarkable achievement for a hobby OS. TCP state machine, DNS resolution, HTTP with chunked encoding all work.
  • Window manager — Damage-rect compositing, z-ordering, taskbar integration, surface-per-window model — solid foundation for a GUI OS.
  • Build system — 117 source files compiled and linked into a bootable ISO with one script. Cross-compilation on Windows works.
  • No phantom code — Every documented feature still exists. Zero abandoned-but-documented features.
